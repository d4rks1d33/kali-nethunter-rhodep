# S3FWRN5 / S3NRN4V HAL disassembly — listen / card-emulation NCI path

Reverse engineering of `nfc_nci_sec.so` (Samsung NFC HAL, AArch64, ~117 KB,
stripped dynsyms + a MiniDebugInfo `.gnu_debugdata`) and
`android.hardware.nfc-service.sec` (the AIDL service, 36 KB, stripped), to find
the exact NCI/proprietary command sequence Android uses to arm NFC-A listen /
card emulation on the Moto G82 (rhodep), and the concrete difference vs mainline
patch 0111.

Method: `readelf`/`nm`/`objdump -d` (GNU binutils 2.42, aarch64), plus manual
decode of the `.rodata` command templates and the `str`/`ldr`-loaded constants.
The MiniDebugInfo section was decompressed (LZMA) to recover the static function
names (`load_rf_binary`, `nfc_hal_state_switch`, `nfc_hal_fw_*`).

Legend: **FACT** = read directly from the disassembly/bytes of the supplied
binaries or configs. **INFERENCE** = derived from NCI 2.0 spec + the code shape.
**UNKNOWN** = not determinable from the supplied material.

---

## TL;DR (the answer to the whole task)

**FACT.** The Samsung HAL does **not** send any proprietary "enable NFC-A listen"
or "enable card-emulation" command, and it does **not** build
`RF_DISCOVER_MAP` / `RF_SET_LISTEN_MODE_ROUTING` (non-clear) / `RF_DISCOVER` /
the `LA_*` `CORE_SET_CONFIG` at all. Every one of those frames is generated by
**Android userspace `libnfc-nci.so`** and passed through the HAL verbatim
(`nfc_hal_write` → `nfc_hal_prehandler` → `device_write`). The HAL is, for the
discovery path, a pure transport plus a handful of *init-time only* proprietary
commands (clock config, rfreg transfer, trace) and two *power/close-time*
proprietary commands.

So there is **no missing magic NCI command in the HAL** that mainline could copy
to make the front-end light up. Confirmed by RE, not inference:

- `nfc_hal_pre_discover` → **sends nothing** (only logs, returns a status byte).
- `nfc_hal_core_initialized` → **sends nothing** (queues the userspace buffer).
- The only routing command the HAL itself emits is `hal_nci_send_clearLmrt`
  = **`21 01 02 00 00`** (LMRT *clear*, 0 entries) — byte-identical to mainline's.
- The proprietary opcodes the HAL emits are `2F 25 / 2F 26 / 2F 27 / 2F 28 /
  2F 2A` (all init: SWAPI-trace / rfreg-transfer / FW-clock-config) and
  `2F 30 01 01` (RTA-store / power-off), and `2F 2F` / `2F 1A` intercepts. **None
  is a listen/CE enable** (details in §3).

The real gap is what the prior RE already concluded from the blob side: this
firmware only lights the NFC-A *listen* analog front-end under the **full Android
userspace NCI/HCE state machine + the vendor `NFA_CORE_SET_CFG` / `NCI_PROP`
config injection mechanism** (§4), which mainline does not reproduce. The
actionable items for patch 0111 are in §7.

## 1. `device_set_mode(eNFC_DEV_MODE)` — it is NOT the RF poll/listen mode (Q4)

FACT (disasm 0xd250):

```
device_set_mode(w0 = mode):
    ioctl(fd, 0x40045301, mode)          ; _IOW('S',1,int) on /dev/sec-nfc
    if mode==2 && prev!=2: clear bss flag
    if mode==1: set bss flag=1
    store mode; if fw_ver>=0x90: usleep(0x186a0=100 ms)
```

- `0x40045301` = `_IOW('S', 0x01, 4)` — the **sec-nfc power/mode ioctl**, i.e.
  the VEN/firmware GPIO state driver, exactly what mainline's `s3fwrn5`
  `s3fwrn5_set_mode()` does over `enable`/`firmware` GPIOs.
- Log string: `"device mode chage: %d -> %d"`.
- **The modes are power states (OFF / ON / BOOTLOADER), not NCI poll/listen/CE.**
  There is **no per-mode NCI/register sequence** here. So the hypothesis "listen
  needs a proprietary `device_set_mode`" is **false** — this function never
  touches RF or NCI. INFERENCE: the enum is `{OFF=0, ON=1, BOOT/FW=2, …}`
  (mode==1 sets an "on" flag, mode==2 is the special/boot path). This is the
  same three-state power model as the mainline driver; nothing is missing here.

## 2. `nfc_hal_rf_set_reg_id_tmp` / `nfc_hal_rf_set_file_tmp` — rfreg *file selectors*, no TX

FACT (disasm 0x10c90 / 0x10d34):

- `nfc_hal_rf_set_reg_id_tmp(u8* p)`: stores `p` into a global (bss); logs
  `"ID: %s"`. Pure setter.
- `nfc_hal_rf_set_file_tmp(char* name, u8 option)`: stores `name` and `option`
  into two globals; logs `"file name: %s"`, `"file option: %d"`. Pure setter.

These choose **which rfreg image file** the transfer path (`hal_vs_get_rf_image`
→ `load_rf_binary` → `hal_vs_rfreg_update*`) will load. FACT — the selectable
variants are only these config keys / paths (from `.rodata` strings):

```
RFREG_FILE            RFREG_FILE_FOR_OLD_HW   RFREG_FILE_FOR_MPOS
RFREG_FILE_FOR_SG     RFREG_FILE_FOR_THL      PATH_FACTORY_RF_REG / PATH_FACTORY_HW_REG
/vendor/etc/sec_s3nsn4v_hwreg_Factory.bin   /vendor/etc/sec_s3nrn82_rfreg_Factory.bin
```

**There is no `RFREG_FILE_FOR_LISTEN` / `_CE` variant.** INFERENCE (matches
`swreg_rfreg_analysis.md`): the HAL loads the **same** hwreg/swreg image for
poll and listen; it does not swap in a listen-specific RF analog profile at
CE-arm. `MPOS` is a merchant/reader (poll) variant, not a listen one.

## 3. Every proprietary (`2F`) command the HAL emits, and when (Q1, Q3, Q5)

### 3.1 The proprietary-frame builder — FACT

`hal_vs_nci_send(u8 oid, u8* payload, size_t len)` (0x157d0) builds:

```
buf[0] = 0x2F            ; GID 0xF (proprietary), MT=command
buf[1] = oid
buf[2] = len
buf[3..] = payload       ; memcpy, capped 255
hal_nci_send(buf)        ; → device_write
```

So **all** vendor commands are `2F <oid> <len> <payload>`.

### 3.2 Init-time proprietary opcodes (the vendor state machine `nfc_hal_vs_sm`, §4) — FACT

Decoded from `nfc_hal_vs_sm` (0x14524) immediates and the rfreg-update helpers:

| opcode | where | meaning |
|--------|-------|---------|
| `2F 26` | `hal_vs_rfreg_update` | legacy rfreg **START** (chip code 0x80–0x83) |
| `2F 22` | (legacy SET) | legacy rfreg **chunk** |
| `2F 27` | `nfc_hal_vs_sm` | legacy rfreg **STOP** |
| `2F 2A` | `hal_vs_rfreg_update_dual_option` | **dual** rfreg (this part, 0x86): sub `01`=start / `02 <idx>`=chunk / `03 <cksum>`=stop |
| `2F 28` | `hal_nci_send_prop_fw_cfg` | **FW clock config** (from `FW_CFG_CLK_TYPE/SPEED/REQ`) |
| `2F 25` | `hal_nci_send_setSWAPITrace` / `nfc_hal_vs_sm` | **SWAPI trace** config (8-byte payload) |

Response/notif opcodes matched in the SM: `0x4f` (`4F ..` prop RSP), `0x6f`
(`6F ..` prop NTF). Chip-code checks `0x74` / `0x84` gate legacy-vs-dual.

`hal_nci_send_prop_fw_cfg` (0x105c0), FACT: header `2F 28`, then fills the
payload from `FW_CFG_CLK_SPEED`, `FW_CFG_CLK_TYPE`, `FW_CFG_CLK_REQ`
(`__get_config_int`), then `__send_to_device`. Called from the FW state machine
during open. **Init clock config, not CE.**

**None of these is a card-emulation / NFC-A-listen enable.** They are all part of
the FW-clock + rfreg-transfer + trace bring-up that mainline already performs via
patch 0104 (`2F 2A` dual rfreg) and the driver's clock handling.

### 3.3 `2F 30 01 01` — FOUND, but it is RTA-store / power-off, not listen (Q3)

The task's `2F 30 …` **does exist** in the binary. FACT:

- `.rodata` at **0x5170** holds the 8-byte template `2f 30 01 01 00 00 00 00`.
- It is loaded by `ldr d1,[x8,#0x170]` (x8 = page 0x5000) and sent (`str s1`
  writes the 4 bytes, then `hal_nci_send`) in exactly two functions:
  - **`nfc_hal_store_rta()`** (0xe9cc), log `"nfc_hal_store_rta: enter;"`.
  - **`nfc_hal_closeForPowerOffCase()`** (0xeb50).
- Both are **exported** and called from the service on **close / power-off**,
  not on discovery. `nfc_hal_pre_discover` does **not** send it.

So the wire frame is `2F 30 01 01` = **prop GID 0xF, OID 0x30, len 1, arg 0x01**.
INFERENCE: OID 0x30 is a "store retained analog / prepare-for-power-off" command
(RTA = Retained/Runtime Analog config). It is emitted so the CLF snapshots its
analog state before the AP powers the chip down (so screen-off SE CE keeps
working). It is **not** a listen/CE arm. (The value in the prior report's docs —
`2F 30 01 00` — is off by the last byte; the real one is `2F 30 01 **01**` and it
is a shutdown-path command, so replaying it in the *discover* path will not help.)

Note (FACT): the adjacent `.rodata` templates at 0x5160 form a small table used
by the prehandler intercepts (§3.4), not a routing/listen table:

```
0x5160: 20 00 01 01   ; CORE_RESET (keep-config)   ← used by the 2F 2F intercept
0x5170: 2f 30 01 01   ; PROP OID 0x30 (RTA/power-off)
0x5178: 4f 1a 01 00   ; PROP RSP 0x1A template     ← used by the 2F 1A intercept
0x5180: 6f ff 01 01   ; PROP NTF 0xFF template
0x5188: 21 01 02 00 00 ; RF_SET_LISTEN_MODE_ROUTING clear (hal_nci_send_clearLmrt)
```

### 3.4 `nfc_hal_prehandler` — the TX intercept (FACT)

`nfc_hal_prehandler(pkt)` (0x10988) runs on every frame libnfc-nci sends. Logic:

```
b = pkt[0] & 0xEF            ; strip the NCI PBF bit
if b == 0x2F:               ; proprietary command from userspace
    oid = pkt[1] & 0x3F
    if oid == 0x1A:         ; PROP 2F 1A → parse pkt[2..] as a duration and
                            ;   program the HAL sleep timer (×1000 / ×60000 ms),
                            ;   then bounce a 4-byte 4F 1A response upward
    if oid == 0x2F:         ; PROP 2F 2F → the HAL swallows it and instead
                            ;   __send_to_device(CORE_RESET '20 00 01 01')
    else: forward to device
if b == 0x40:               ; a GID-0 frame with OID 0 (reset echo)
    if (pkt[1] & 0x3F)==0:  rewrite pkt[0..1] = 2F 4F  (mark as prop)
if b == 0x6F:               ; PROP NTF; OID 1 → sleep-timer housekeeping
else: forward to device (return 1)
```

Key point (FACT): the prehandler **only** special-cases the Samsung sleep-timer
(`2F 1A`) and a `2F 2F`→CORE_RESET shim. It does **not** inject any listen/CE
command, does **not** rewrite `CORE_SET_CONFIG` (`20 02`), `RF_DISCOVER_MAP`
(`21 00`), `RF_SET_LISTEN_MODE_ROUTING` (`21 01`) or `RF_DISCOVER` (`21 03`).
Those pass straight through to `device_write` unmodified. **This proves the
listen/discovery NCI is authored entirely by userspace libnfc-nci, byte-for-byte
as it hits the wire.**

## 4. The `NFA_CORE_SET_CFG` / `NCI_PROP` config-injection mechanism (the real vendor hook)

This is the one place the HAL can push *arbitrary* NCI, and it is driven **from
the .conf file**, not hard-coded.

### 4.1 `hal_nci_send_core_set_conf()` — FACT (0x1028c)

```
CNfcConfig::GetInstance()
n = getValue("NFA_CORE_SET_CFG", buf, 252)     ; a byte-array from the .conf
if n <= 3: error "Invalid len of core set configuration data"
frame = 20 02 <n> <buf[0..n-1]>                ; CORE_SET_CONFIG, GID1 OID2
__send_to_device(frame)                         ; log "Vendor: Set core set configurations"
```

Called once from `nfc_hal_vs_sm` right after the rfreg update + clearLmrt, during
**HAL open/postinit** (state machine reaches this after `2F 25` SWAPI-trace).
INFERENCE: `NFA_CORE_SET_CFG` is the vendor's way to program controller
`CORE_SET_CONFIG` TLVs at boot (RF analog/protocol tuning params the firmware
wants set before discovery). **Our supplied `libnfc-sec-vendor.conf` does NOT
contain this key** (FACT — grep verified), so on this dump the HAL sends nothing
here. On the phone's *real* vendor conf it may carry listen-relevant TLVs.

### 4.2 `NCI_PROP` — arbitrary proprietary commands from the .conf — FACT

- `get_config_propnci_get_oid(idx)` (0x17b48): opens
  `/vendor/etc/libnfc-sec-vendor.conf` (fallback `/etc/…`), finds the
  `(idx+1)`-th line whose key is **`NCI_PROP`**, `strtol`s its value (hex if
  `0x`), returns it as the **OID** (must be < 0x100).
- `hal_vs_get_prop(idx, pkt)` (0x15880): calls the above to get the OID, then
  `sprintf(key, "NCI_PROP0x%02X", oid & 0x3F)` and
  `get_config_byteArry(key, &pkt[3], 255)` to read that command's **payload**.
  Builds `pkt = [_, oid, len, payload…]` (the leading `2F` added by the send path).

So the vendor mechanism is: put lines like

```
NCI_PROP=0x30
NCI_PROP0x30={01}
```

in `libnfc-sec-vendor.conf`, and the HAL will emit `2F 30 01 01`, etc., during
bring-up. FACT: **neither `NCI_PROP` nor `NCI_PROP0x..` is present in the supplied
`libnfc-sec-vendor.conf`**, and `get_config_count("NCI_PROP")` is not called from
within the .so — the *iteration* over these entries is done by whichever
component owns the open sequence (the vendor’s open state machine /
`nfc_hal_open_sm` via the exported getters). On this dump, zero `NCI_PROP`
entries ⇒ zero extra prop commands.

**Conclusion for §4:** the HAL has a fully data-driven path to send extra
`CORE_SET_CONFIG` and arbitrary `2F` prop commands at init — but it is *empty* in
the conf we have. If Android on this exact device *did* rely on a listen-enabling
prop command or CORE_SET_CONFIG, it would live in the **complete** vendor
`libnfc-sec-vendor.conf` under `NFA_CORE_SET_CFG` / `NCI_PROP*`, which the supplied
dump does not contain. **This is the single most valuable thing left to capture.**

trust the measured `NFCEE_DISCOVER_NTF` (0x83 = MIFARE/eSE). (INFERENCE: the
mismatch is why blindly copying conf route ids would misroute; use the enumerated
NFCEE id.)

## 6. Byte-exact vendor listen/CE sequence

**FACT.** The HAL does not author the listen/CE NCI. What the HAL *does* emit, in
order, is the bring-up sequence below; everything after "→ userspace" is
generated by libnfc-nci and only *transported* by the HAL:

```
HAL open / init (nfc_hal_open_sm → nfc_hal_fw_sm → nfc_hal_vs_sm):
  1. device_set_mode(BOOT)              ; ioctl 0x40045301 (GPIO), no NCI
  2. 20 00 01 01                        ; CORE_RESET (keep config)   [hal_nci_send_reset]
  3. 20 01 02 00 00                     ; CORE_INIT (NCI 2.0)         [hal_nci_send_init]
  4. 2F 28 <len> <clk…>                 ; PROP FW clock cfg           [hal_nci_send_prop_fw_cfg]
  5. 2F 2A 01 …                         ; dual rfreg START            [hal_vs_rfreg_update_dual_option]
     2F 2A 02 <idx> <252B chunk> …      ; dual rfreg chunks (rfreg∥swreg)
     2F 2A 03 <cksum16>                 ; dual rfreg STOP (cksum 0x5B9A)
  6. 2F 25 <8B>                         ; SWAPI trace cfg             [hal_nci_send_setSWAPITrace]
  7. 21 01 02 00 00                     ; RF_SET_LISTEN_MODE_ROUTING **clear** [hal_nci_send_clearLmrt]
  8. 20 02 <len> <NFA_CORE_SET_CFG>     ; CORE_SET_CONFIG  *iff* key present (absent in our conf)
  9. (for each NCI_PROP entry in .conf) 2F <oid> <len> <payload>   ; absent in our conf
  --- HAL hands over; libnfc-nci now drives discovery over nfc_hal_write ---
  → 20 02 …   CORE_SET_CONFIG   (LA_*/LF_*/routing params, authored by userspace)
  → 21 00 …   RF_DISCOVER_MAP   (userspace)
  → 21 01 …   RF_SET_LISTEN_MODE_ROUTING  (userspace, non-clear, real entries)
  → 21 03 …   RF_DISCOVER       (userspace)
```

The canonical AOSP order libnfc-nci uses at steps →: **CORE_SET_CONFIG →
RF_DISCOVER_MAP → RF_SET_LISTEN_MODE_ROUTING → RF_DISCOVER** (INFERENCE, standard
NFA `nfa_dm`/`nfa_ee` sequencing; the HAL passes them in that order untouched).

The only HAL-authored routing frame is the **clear** at step 7
(`21 01 02 00 00`), byte-identical to mainline's `hal_nci_send_clearLmrt`. The
`2F 30 01 01` prop command is **not** in this path — it is close/power-off only
(§3.3).

## 7. Concrete difference vs patch 0111, and what to change (Q4)

Overriding FACT from `nfc.md`: the chip accepts all of 0111's
SET_CONFIG/MAP/LMRT/DISCOVER with `status 0x0`, does NFC-F/NFC-DEP listen, but
never lights NFC-A listen at RF — with a Flipper too. The RE confirms the HAL
adds **no secret NCI command**, so the difference is in *how* the standard NCI is
composed + the vendor config injection, plus the RF profile:

1. **Command ORDER (FACT it differs).** 0111 sends the LMRT *before*
   `RF_DISCOVER_MAP` (it calls `nci_request(...lmrt...)` inside `nci_start_poll`
   ahead of the map/discover flow). Android/libnfc-nci order is **SET_CONFIG →
   DISCOVER_MAP → LMRT → RF_DISCOVER**. **Reorder 0111 to MAP → LMRT →
   DISCOVER.** (Cheapest, highest-value; some firmwares only commit the LMRT
   against the already-installed MAP.)

2. **Stray host routes in the LMRT (FACT).** 0111's LMRT also routes NFC-F +
   NFC-DEP to host with no matching LISTEN `RF_DISCOVER_MAP` entry. Android's HAL
   only ever emits a *clear* LMRT itself; the real table comes from NFA and is
   consistent (every routed activatable protocol has a listen map). For the
   eSE/MIFARE goal, **drop the host F/DEP LMRT entries** and keep only NFC-A
   technology + T2T + MIFARE(0x80). For the host-CE goal, keep A-tech + T2T.

3. **Power-state byte (INFERENCE).** The measured Android offhost power mask is
   **`OFFHOST_AID_ROUTE_PWR_STATE=0x3B`** (FACT, from `libnfc-nci.conf`). 0111
   uses `0x3f`. Use **`0x3B`** in the LMRT entries (bit2 is not a supported power
   state on this part; `0x3f` can be accepted yet not applied).

4. **The vendor `NFA_CORE_SET_CFG` / `NCI_PROP` injection (FACT the mechanism
   exists; UNKNOWN its listen contents).** The HAL supports pushing extra
   `CORE_SET_CONFIG` TLVs and arbitrary `2F` commands from
   `libnfc-sec-vendor.conf`, but the supplied conf has **none**. If Android
   depends on a listen-relevant TLV/prop here, mainline is missing it. **Capture
   the complete on-device `/vendor/etc/libnfc-sec-vendor.conf`** and look for
   `NFA_CORE_SET_CFG=` and any `NCI_PROP=/NCI_PROP0x..=` lines; those bytes are
   the only vendor-secret candidates and are trivially replayable in the driver.

5. **The RF analog listen profile (INFERENCE, strongest root cause).** Confirmed
   from both sides now: (a) the rfreg/swreg blobs are a poll/TX image with no
   NFC-A listen matrix (`swreg_rfreg_analysis.md`), and (b) the HAL loads the
   **same** rfreg for poll and listen — there is no `RFREG_FILE_FOR_LISTEN`, and
   `nfc_hal_rf_set_file_tmp` only selects among poll/factory/MPOS variants. So on
   Android the NFC-A listen front-end is lit either by (i) firmware behavior that
   only triggers under the full NFA listen state (the userspace stack mainline
   lacks) or (ii) a `NFA_CORE_SET_CFG`/`NCI_PROP` TLV from the full vendor conf
   (item 4). It is **not** a distinct RF blob mainline can load.

**Net:** apply 1+2+3 to patch 0111 (order, prune stray routes, `0x3B` power). If
the A front-end still stays dark, the remaining difference is **item 4** — the
untruncated `libnfc-sec-vendor.conf` (`NFA_CORE_SET_CFG` / `NCI_PROP`) — which is
the last unread vendor input and the only place a listen-enabling command could
hide. There is **no hidden HAL opcode** to add.

## 8. Direct answers to the six task questions

1. **Disassembled RF/listen/mode functions & their commands:** `device_set_mode`
   = sec-nfc power ioctl `0x40045301` (no NCI). `nfc_hal_rf_set_reg_id_tmp` /
   `nfc_hal_rf_set_file_tmp` = rfreg file/id selectors (no NCI).
   `hal_nci_send_prop_fw_cfg` = `2F 28` FW clock (init). Proprietary opcodes seen:
   `2F 25` (trace), `2F 26/22/27` (legacy rfreg), `2F 28` (clock), `2F 2A` (dual
   rfreg), `2F 30 01 01` (RTA/power-off), plus prehandler intercepts `2F 1A`
   (sleep timer) and `2F 2F`→CORE_RESET. **No CE-enable prop command exists.**

2. **CE/listen sequence & order:** the HAL authors none of it beyond an LMRT
   *clear* (`21 01 02 00 00`) and an optional conf-driven `CORE_SET_CONFIG`
   (`NFA_CORE_SET_CFG`, absent here). SET_CONFIG/MAP/LMRT/DISCOVER are authored by
   userspace libnfc-nci in the order SET_CONFIG → MAP → LMRT → DISCOVER and only
   transported. **No extra `2F` "turn on the A front-end" frame.**

3. **`2F 30 01 00`:** the real command is **`2F 30 01 01`** and it is sent by
   `nfc_hal_store_rta()` and `nfc_hal_closeForPowerOffCase()` — **RTA-store /
   power-off**, not listen. `NFCEE_POWER_AND_LINK_CTRL (21 03)`: **the HAL never
   builds it**; the `21 03` byte pairs in `.text` are incidental instruction
   encodings, and the HAL's discovery path emits nothing (if Android sends
   `21 03`, it is from userspace NFA, not this HAL).

4. **`device_set_mode` modes:** power states (OFF/ON/BOOT) via GPIO ioctl only;
   **no per-mode NCI/register sequence, no listen mode**. Not the missing piece.

5. **Config:** all KEY=VALUE extracted in §5. Notable: no
   `HOST_LISTEN_TECH_MASK`; `P2P_LISTEN_TECH_MASK=0x44` (no A bit);
   `OFFHOST_AID_ROUTE_PWR_STATE=0x3B`; `NFA_PROPRIETARY_CFG` index5=0x80 (MIFARE);
   `DEFAULT_ROUTE=0x83` is an AOSP route-index, not the raw NFCEE id.

6. **The exact sequence to replicate:** §6. The HAL contributes only
   `20 00 01 01` / `20 01 02 00 00` / `2F 28…` / `2F 2A…` / `2F 25…` /
   `21 01 02 00 00` at init; the listen SET_CONFIG/MAP/LMRT/DISCOVER are standard
   NCI from userspace. The actionable driver change is items 1–3 of §7, and the
   decisive unread input is the full `libnfc-sec-vendor.conf`
   (`NFA_CORE_SET_CFG`/`NCI_PROP`).

## 9. FACT / INFERENCE / UNKNOWN

**FACT**
- `device_set_mode` = ioctl `0x40045301` on `/dev/sec-nfc`, no NCI/RF.
- `nfc_hal_pre_discover` and `nfc_hal_core_initialized` send **no** NCI.
- Only HAL-authored routing frame = `hal_nci_send_clearLmrt` = `21 01 02 00 00`.
- Proprietary opcodes emitted: `2F 25/26/22/27/28/2A` (init), `2F 30 01 01`
  (RTA/power-off in `nfc_hal_store_rta` + `nfc_hal_closeForPowerOffCase`), plus
  prehandler `2F 1A`/`2F 2F` intercepts.
- `hal_vs_nci_send` frames all prop cmds as `2F <oid> <len> <payload>`.
- `hal_nci_send_core_set_conf` sends `20 02 <NFA_CORE_SET_CFG>` from the .conf.
- `get_config_propnci_get_oid` + `hal_vs_get_prop` read `NCI_PROP` / `NCI_PROP0xNN`
  from `/vendor/etc/libnfc-sec-vendor.conf`.
- The prehandler does **not** rewrite `20 02 / 21 00 / 21 01 / 21 03`.
- Supplied `libnfc-sec-vendor.conf` has **no** `NFA_CORE_SET_CFG`/`NCI_PROP*`/
  `HOST_LISTEN_TECH_MASK`/`LA_*`/`LF_*`.
- `NFA_PROPRIETARY_CFG` index 5 = 0x80 (MIFARE); `OFFHOST_AID_ROUTE_PWR_STATE=0x3B`;
  `P2P_LISTEN_TECH_MASK=0x44` (no NFC-A bit).
- The service binary is a thin AIDL wrapper with no routing/prop logic.

**INFERENCE**
- OID 0x30 = "store retained analog / prep-for-power-off" (name RTA + call sites).
- The NFC-A listen front-end is armed by the full NFA userspace listen state
  and/or a `NFA_CORE_SET_CFG`/`NCI_PROP` TLV in the *complete* vendor conf, not by
  a distinct RF blob or a hidden HAL opcode.
- Patch 0111 fixes: reorder MAP→LMRT→DISCOVER, prune stray host F/DEP LMRT
  routes, use power byte `0x3B`.
- `device_set_mode` enum ≈ {OFF=0, ON=1, BOOT/FW=2}.

**UNKNOWN**
- The contents of the *complete* on-device `libnfc-sec-vendor.conf`
  (`NFA_CORE_SET_CFG=` bytes, any `NCI_PROP*` entries) — the supplied copy has
  none. This is the last unread vendor input and the only remaining place a
  listen-enabling command/TLV could live. **Capture it next**, plus a live NCI
